# MINTIFY – Architecture Overview

## What this system is

MINTIFY is a German-language RAG (Retrieval-Augmented Generation) chat system built for
financial education research at Hochschule Bonn-Rhein-Sieg. Users ask questions in a browser
and receive answers grounded in uploaded PDF documents, generated by a large language model
running on RunPod GPU infrastructure.

The system is split into four Docker containers plus one remote service, each with a single
clear responsibility. This separation means ML dependencies (PyTorch, sentence-transformers)
are isolated in one container and don't bloat the others.

## Request lifecycle — from keystroke to streamed token

Every chat message travels through this exact sequence:

**1. User types and sends a message** in the browser at `localhost:3000`.

**2. OWUI frontend** (SvelteKit, runs in the browser) sends a streaming fetch to its own
   Python backend at `/api/chat/completions`.

**3. OWUI backend** (`open-webui-src/backend/open_webui/routers/openai.py`, line 588)
   detects that the selected model is a pipeline model (model ID starts with `mintify_pipeline.`)
   and forwards the request as an OpenAI-compatible `POST /chat/completions` to:
   ```
   http://pipelines:9099/chat/completions
   ```
   It injects user metadata into the payload and passes the API key from:
   ```
   OPENAI_API_BASE_URL=http://pipelines:9099
   OPENAI_API_KEY=mintify-pipeline-key
   ```

**4. Pipelines framework** (inside `mintify-pipelines`) receives the request, looks up the
   registered pipeline by model ID, and calls `Pipeline.pipe()` in `mintify_pipeline.py`.

**5. `mintify_pipeline.pipe()`** (`pipelines/mintify_pipeline.py`):
   - Strips the pipeline namespace prefix from the model ID:
     `mintify_pipeline.Qwen__Qwen3-1.7B` → `Qwen/Qwen3-1.7B`
   - Builds a JSON payload containing the user message, model ID, conversation history,
     temperature, system prompt, and top_k.
   - Opens a streaming POST to `http://mintify-rag-service:8080/api/pipe`.
   - Yields each text chunk from the response back to the OWUI framework.

**6. `mintify-rag-service` POST /api/pipe** (`rag-backend/app/routers/rag.py`):
   a. `indexer.index_new_files()` — check for new PDFs (hash-based, fast if nothing new)
   b. `embedder.encode(user_message)` — convert query to a 384-dim float vector
   c. `retriever.retrieve(query_vec, top_k)` — cosine similarity search in Qdrant,
      returns top-K chunk texts formatted with source citations
   d. `system_prompt.format(context=chunks)` — inject retrieved chunks into the German
      system prompt's `{context}` placeholder
   e. Build enriched message list: `[system_with_context] + conversation_history`
   f. `llm.stream(enriched_messages, model_id, temperature)` — call vLLM on RunPod
      via the OpenAI client, yield token deltas as plain text

**7. vLLM on RunPod** generates the answer and streams tokens back through:
   `RunPod → SSH tunnel → localhost:8002 → host.docker.internal:8002 → rag-service → pipelines → OWUI → browser`

**8. Browser** receives tokens progressively and appends them to the chat bubble in real time.

## Data formats at each boundary

| Boundary | Protocol | Format |
|---|---|---|
| Browser → OWUI frontend | HTTP | Internal SvelteKit fetch |
| OWUI frontend → OWUI backend | HTTP | OpenAI chat completions (streaming) |
| OWUI backend → pipelines | HTTP POST `/chat/completions` | OpenAI JSON: `{model, messages, stream, temperature, ...}` |
| Pipelines → rag-service | HTTP POST `/api/pipe` | Custom JSON: `{user_message, model_id, messages, temperature, system_prompt, top_k}` |
| rag-service → vLLM | HTTP POST `/v1/chat/completions` | OpenAI JSON (streaming SSE) |
| vLLM → rag-service | SSE stream | `data: {"choices": [{"delta": {"content": "token"}}]}` |
| rag-service → pipelines | HTTP streaming | `text/plain` — raw token strings |
| Pipelines → OWUI | HTTP streaming | `text/plain` — same raw tokens |
| OWUI → browser | HTTP streaming | SSE wrapping the token stream |

## PDF indexing pipeline

PDFs are uploaded to `./data/uploads/` on the host (bind-mounted to `/app/uploads` in
the `mintify-rag-service` container). Indexing happens in two moments:

**At startup** (`Indexer.startup()` called from `dependencies.init_singletons()`):
1. Connect to Qdrant, create the `mintify_rag` collection if missing (384-dim, cosine)
2. Scroll all existing Qdrant points to load known `file_hash` values into memory
   (prevents re-embedding already-indexed files on container restart)
3. Scan `/app/uploads/**/*.pdf`, skip hashes already in the set, index the rest

**At query time** (`Indexer.index_new_files()` called on every `/api/pipe` request):
- Same hash check — only processes files uploaded after the last startup
- No Qdrant read needed; the in-memory hash set is consulted

**Per-file indexing** (`Indexer._index_file()`):
1. Compute MD5 hash of file bytes (dedup key)
2. Open PDF with PyMuPDF, extract text page by page
3. Split each page's text into overlapping chunks:
   - `chunk_size = 800` characters
   - `chunk_overlap = 100` characters (10-char overlap prevents boundary splits)
4. Embed each chunk: `Embedder.encode(chunk)` → 384-dim float list
5. Assign deterministic Qdrant ID: `int(md5_hex, 16) % (2**53) + page*1000 + chunk_i`
   (same file always produces same IDs → upsert is idempotent, no duplicates)
6. Batch upsert all PointStructs to Qdrant with payload: `{text, source, page, file_hash}`

## Model routing — how RunPod models appear in the dropdown

The model dropdown in OWUI is populated through a chain of three hops:

```
OWUI polls GET /models on the pipelines server
  → pipelines calls pipelines() in mintify_pipeline.py
    → mintify_pipeline.py calls GET http://mintify-rag-service:8080/api/models
      → rag-service calls GET {vllm_url}/v1/models on each configured vLLM URL
        → vLLM returns {"data": [{"id": "Qwen/Qwen3-1.7B"}, ...]}
```

**ID sanitization** (required because HuggingFace IDs contain `/` which breaks URL routing):
- Outbound (in `pipelines()`): `Qwen/Qwen3-1.7B` → `Qwen__Qwen3-1.7B`
- OWUI registers the model as: `mintify_pipeline.Qwen__Qwen3-1.7B`
- Inbound (in `pipe()`): `mintify_pipeline.Qwen__Qwen3-1.7B` → `Qwen/Qwen3-1.7B`
- The raw HuggingFace ID is what vLLM expects in the `model` field

**Multi-instance routing** (`LLMClient._model_url_map`):
- If two vLLM pods are running (ports 8002 and 8004), the map holds both:
  `{"Qwen/Qwen3-1.7B": "http://host.docker.internal:8002", "Qwen/other": "http://host.docker.internal:8004"}`
- `_resolve_url(model)` looks up the correct URL for each request
- If a model isn't found (stale map), it refreshes once before falling back

## Configuration system

Settings are layered: docker-compose env vars override Python defaults.

**`rag-backend/app/config.py`** (`Settings` class, read by `pydantic-settings`):

| Setting | Env var | Default | Description |
|---|---|---|---|
| `vllm_base_urls` | `VLLM_BASE_URLS` | `host.docker.internal:8002,...` | Comma-separated vLLM URLs |
| `qdrant_url` | `QDRANT_URL` | `http://qdrant:6333` | Qdrant REST endpoint |
| `collection_name` | — | `mintify_rag` | Qdrant collection name |
| `embedding_model` | — | `all-MiniLM-L6-v2` | SentenceTransformer model |
| `upload_dir` | `UPLOAD_DIR` | `/app/uploads` | PDF directory |
| `chunk_size` | — | `800` | Characters per chunk |
| `chunk_overlap` | — | `100` | Overlap between chunks |
| `top_k` | — | `5` | Default retrieved chunks per query |

**`pipelines/mintify_pipeline.py`** (`Valves` class, editable live in Admin Panel → Pipelines):

| Valve | Default | Description |
|---|---|---|
| `BACKEND_URL` | `$RAG_BACKEND_URL` | RAG service URL |
| `TOP_K` | `5` | Overrides rag-service default |
| `SYSTEM_PROMPT` | German prompt | Must contain `{context}` |

Valve changes are persisted to `pipelines/mintify_pipeline/valves.json` by OWUI
and reloaded automatically on the next pipeline reload (or container restart).

## Docker networking

All four containers are on the same Docker bridge network created by `docker compose`.
Docker's internal DNS resolves container names:

| From | To | Hostname used |
|---|---|---|
| `mintify-webui` | `mintify-pipelines` | `pipelines` (service name) |
| `mintify-pipelines` | `mintify-rag-service` | `mintify-rag-service` (container name) |
| `mintify-rag-service` | `mintify-qdrant` | `qdrant` (service name) |
| `mintify-rag-service` | vLLM on host | `host.docker.internal` |

`host.docker.internal` is a special Docker Desktop hostname that resolves to the
host machine's IP from inside a container. The SSH tunnel (`scripts/runpod-tunnel.sh`)
binds RunPod's vLLM port to `localhost:8002` on the host, which is then reachable
from containers as `host.docker.internal:8002`.

## Startup sequence and container dependencies

```
docker compose up -d

1. qdrant         starts immediately — no dependencies
2. mintify-rag-service  starts after qdrant (condition: service_started)
   └── loads embedding model, indexes PDFs, queries vLLM for models
   └── /api/health returns 503 during this phase (~60-120s)
   └── /api/health returns 200 when ready
3. pipelines      starts after rag-service is healthy (condition: service_healthy)
   └── loads mintify_pipeline.py, calls on_startup(), calls pipelines()
4. open-webui     starts after pipelines (no health check, just depends_on)
```

**What breaks if something is down:**

| Missing | Effect |
|---|---|
| RunPod tunnel not running | `GET /api/models` returns `[{id:"unavailable"}]`; prompts get no LLM response |
| Qdrant down | RAG search fails; LLM still responds but without PDF context |
| rag-service down | Pipeline `pipe()` logs `ERROR calling RAG backend`; user sees German error in chat |
| pipelines down | OWUI shows no models in dropdown |

## Debugging reference

| What you want to see | Command |
|---|---|
| Pipeline invocation + model routing | `docker logs -f mintify-pipelines` |
| Full RAG trace (chunks retrieved, scores) | `docker logs -f mintify-rag-service` |
| OWUI errors (DB, auth, routing) | `docker logs -f mintify-webui` |
| Number of indexed vectors | `curl http://localhost:6333/collections/mintify_rag` |
| Which models vLLM sees | `curl http://localhost:8002/v1/models` |
| Last retrieved chunks for a query | `docker logs mintify-rag-service 2>&1 \| grep -A 20 "pipe() called" \| tail -30` |

**Log prefixes:**

| Prefix | Container | Meaning |
|---|---|---|
| `[MINTIFY]` | `mintify-pipelines` | Pipeline proxy events (startup, model registration, pipe() calls) |
| `[RAG]` | `mintify-rag-service` | RAG pipeline events (indexing, embedding, retrieval, vLLM calls) |

**Hot-reload:** Saving `pipelines/mintify_pipeline.py` triggers automatic reload in the
running container (bind-mounted volume + file watcher). For rag-backend changes, rebuild:
```bash
docker compose up -d --build mintify-rag-service
```

**Wipe and re-index:**
```bash
docker compose down
rm -rf data/qdrant/
docker compose up -d
```
The indexer will re-embed all PDFs from scratch on the next startup.
